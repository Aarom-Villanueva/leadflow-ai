## 10. Respuesta al hallazgo único de la cuarta ronda (candidato corregido `d5e7b2c1b72144c74f05a53782efbc2b970b935b` → este commit)

**Resultado incierto del cierre transaccional**: en `transaction-instrumentation.ts`, una excepción al enviar COMMIT o ROLLBACK se registraba incondicionalmente como `'rolledback'`. Eso inventaba una confirmación: una excepción al enviar COMMIT no prueba que el servidor no lo haya aplicado — la conexión pudo perderse DESPUÉS de que el servidor confirmara el commit y ANTES de que el cliente recibiera esa respuesta. Asumir `'rolledback'` ahí es tan falso como asumir `'committed'`.

Corrección: se añade un cuarto estado a `TransactionOutcome`: `'open' | 'committed' | 'rolledback' | 'unknown'`.
- `result.command === 'COMMIT'` → `'committed'`.
- `result.command === 'ROLLBACK'` (incluso al enviar texto `commit`, transacción abortada server-side) → `'rolledback'`.
- Excepción durante el envío de COMMIT/ROLLBACK, o una respuesta exitosa con un tag de cierre no reconocido (ni `'COMMIT'` ni `'ROLLBACK'`) → `'unknown'`, nunca `'rolledback'` supuesto.
- En los tres casos se conserva el mensaje de error en `trace.error` (cuando lo hay) y se limpia `currentRealTransactionId` de todos modos: ninguna consulta posterior hereda el identificador de una transacción cuyo cierre quedó incierto, sea cual sea el motivo del cierre.

Se corrigió la prueba que exigía `'rolledback'` cuando el propio COMMIT lanzaba (ahora exige `'unknown'`, con un mensaje de error que describe una conexión perdida, no un conflicto de serialización — más fiel al escenario real que motiva este hallazgo). Se añadieron dos regresiones nuevas: ROLLBACK con la respuesta perdida (`'unknown'`, con la limpieza del estado de transacción activa verificada explícitamente sobre una consulta posterior) y un tag de cierre inesperado en una respuesta exitosa (`'unknown'`, nunca inferido del texto enviado). Las 10 pruebas de `transaction-instrumentation.test.ts` siguen usando el mismo doble inyectado sobre el módulo real; ninguna sustituye la comprobación pendiente contra PostgreSQL real.

**Ejecutado en esta ronda**: `npx vitest run` → **82/82** pruebas puras en 8 archivos (2 netas más que la ronda anterior). `node --test tests/coordination/*.test.mjs` → **217/217**, sin regresión. `npm run lint` → limpio. `npm run typecheck` → 36 errores, mismo patrón exacto de cascada, confirmado línea por línea, ningún error nuevo.
