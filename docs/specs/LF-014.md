# LF-014 — Verificación Git obligatoria de los estados done del backlog (B6)

**Estado:** propuesta de implementación read-only pendiente de revisión. Responsable ChatGPT, revisor propuesto Claude Code.
**Base:** merge PR #9 en `main` `c160de9c9424918381d3bb67d64f729a0907e8db`.

## Problema

B6 identificó que el valor `status:"done"` en `docs/autopilot/BACKLOG.json` podía ser editado como JSON sin demostrar por sí mismo que el merge existía en Git. El chequeo de reservas de HANDOFF ya verifica los padres de merge y la ancestralidad.

## Solución acotada

- Añadir `scripts/autopilot/check-done-proof.mjs`, que **solo lee** el backlog anterior y actual, HANDOFF y commits Git usando `git show`, `git rev-list`, `git merge-base`.
- En cada PR, para cada tarea `done` en el backlog, exigir reserva `completed` en HANDOFF con el mismo propietario, `head_sha` y `merge_sha` válidos, merge con al menos dos padres y uno igual al head auditado, merge ancestro del `BASE_SHA` confiable, y mensaje que mencione el ID de tarea.
- Impedir que se degrade o borre una tarea previamente `done` sin una migración de esquema aprobada. Ante errores, negar con exit no-cero y bloquear el check obligatorio de coordinación.
- Añadir al job existente `Coordination gate` de `.github/workflows/ci.yml` el paso de verificación; no añadir tokens, permisos, proveedores, ejecuciones ni gastos.
- Añadir pruebas sintéticas para evidencia válida, prueba falsa, falta de ancestro, cambio de estado, duplicados, ausencia de registro e invalidación de la bandera `execution_enabled`.
- Cerrar LF-013 usando evidencia de merge PR #9, y reservar todos los archivos de este PR en ROADMAP/HANDOFF.

## Criterios de aceptación

1. `node --test tests/coordination/*.test.mjs` en Node 24, y ambos checks obligatorios de GitHub `success` para SHA del PR.
2. `node scripts/autopilot/check-done-proof.mjs --base <BASE_SHA> --head <HEAD_SHA>` identifica `LF-001a` como tarea `done` respaldada por merge real.
3. Pruebas negativas de prueba falsificada y rollback rechazan de forma segura. No usar el propio commit del PR (head) como prueba de un merge anterior.
4. `docs/autopilot/BACKLOG.json` permanece **intacto** con `execution_enabled=false`, `LF-002a` bloqueado, y `LF-002`/`LF-003` bloqueadas.
5. Auditoría de Claude del SHA exacto y autorización expresa del propietario antes de fusionar.

## Riesgos y límites explícitos

- Esto fortalece la prueba de **historial** de Git en un PR, no es un control de aprobación comercial, presupuesto ni ejecución. No sustituye validación de especificación, permisos y costo.
- Se confía en `BASE_SHA` derivado del evento GitHub Actions y en la protección de `main` (no en una aseveración del agente). Una nueva tarea solo puede quedar `done` tras un merge ya incluido en la base.
- Un job de CI que hace checkout de código del PR no debe recibir secretos. Para ejecución real futura se requiere separar confianza y volver a analizar dónde vive este código de validación.
- No se permite modificar la ruleset, emplear APIs de IA ni habilitar dispatcher. Se conserva la política de revisión independiente, pruebas y aprobación humana.
