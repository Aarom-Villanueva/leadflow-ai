## Contrato

- Better Auth usa las tablas globales verificadas en LF-023 y el paquete fijado en el lockfile. Sin cambios de versiones ni proveedores externos.
- `/api/auth/*`: GET/POST adaptados a Better Auth. POST exige origen configurado; límites persistidos para login/registro. Errores públicos seguros.
- `/api/organizations`: GET lista únicamente membresías vigentes; POST valida estrictamente name/slug/timezone y crea organización, owner y auditoría atómicamente. No acepta rol, actor ni organización del cliente como autoridad.
- `/api/organizations/:id`: GET valida sesión y membresía activa. IDs inexistentes/ajenos responden 404. `/administration` exige owner/admin y responde 403 a sales.
- Base separada del laboratorio. Runtime no propietario, sin superusuario/BYPASSRLS/CREATEROLE/CREATEDB; RLS para lectura de organizations/memberships. Mutaciones de bootstrap solo por una función SQL security definer mínima, con search_path fijo, sin permisos PUBLIC y sin DML directo del runtime sobre tablas de organización. Su propietario es el provisionador, no el runtime. No se usa FORCE en esas tablas para permitir este bootstrap revisable del propietario; runtime siempre sujeto a RLS. No hay funciones de elevar rol o borrar propietarios.
- Contexto app.user_id transaction-local desde sesión validada, nunca persistente en conexión. Cada petición vuelve a validar membresía; no cachear permisos ni sesiones revocadas.
- Configuración requerida solo al usar identidad; build y prototipo funcionan sin DB/secret. Sin valores secretos por defecto. Migración explícita con credencial separada, nunca automática en arranque.
- Desarrollo sin correo: la UI explica que verificación/recuperación aún no están disponibles. No habilitar producción con datos reales con esta entrega.
