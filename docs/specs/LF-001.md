# LF-001 — Base técnica reproducible

Estado: propuesta, bloqueada por aprobación LF-000 y D-001. Responsable propuesto: Codex. Revisor: Claude Code. No autoriza instalar ni implementar durante LF-000.

## Objetivo y alcance
Preparar la base Next.js/React/TypeScript, Tailwind, Zod, Vitest, Playwright y GitHub Actions, con estructura modular y configuración de entorno validada. Evaluar compatibilidad de Drizzle/Better Auth/PostgreSQL para informar LF-002 sin implementar autenticación. No crear tablas de negocio, correo, IA real, infraestructura paga o producción.

## Decisiones y contratos previos
Confirmar versiones compatibles mediante documentación oficial y una instalación verificada; elegir versión Node LTS soportada y fijar package manager/versiones/lockfile. Propuesta npm por disponibilidad, no decisión cerrada. Documentar comandos install/dev/lint/typecheck/test/build/e2e y variables por nombre, ejemplos sin secretos. Variables server-only nunca llevan prefijo público. Configuración compartida solo cambia con revisión.

Rutas previstas: package.json, package-lock.json si npm aprobado, pin de Node, tsconfig.json, next.config.*, src/app/**, src/modules/**, src/shared/config/**, tests/**, playwright.config.*, vitest.config.*, .github/workflows/ci.yml, .env.example, README.md. Reservar estos archivos para Codex hasta merge; Claude revisa sin editarlos simultáneamente.

## Criterios de aceptación
1. Checkout limpio en Node fijado: instalación congelada exitosa sin modificar lockfile; README contiene comandos exactos y limitaciones.
2. Página inicial accesible y endpoint de salud no sensible responden mediante request real. Sin datos demo que aparenten CRM funcional. Config faltante falla con nombre de variable y sin valores.
3. TypeScript estricto, lint y build concluyen sin errores. Vitest ejecuta comportamiento real del validador de configuración (válida/inválida, sin filtrar secretos); no suite vacía.
4. Playwright abre página y comprueba contenido/teclado básico; un fallo de servidor hace fallar la prueba. No acceso a OpenAI ni correo externo.
5. CI reproduce instalación, tipos, pruebas y build; instalar navegadores requeridos con verificación TLS. Actions fijadas por SHA, permisos read-only y sin secretos en PR no confiable.
6. Registrar recursos y límites de hosting candidato, toolchain, compatibilidad de Better Auth/Drizzle y decisión de acceso DB/pooling/RLS pendiente de LF-002. No afirmar aislamiento validado sin integración real posterior.
7. CI incluye un check que compara los archivos modificados del PR contra la columna "Archivos previstos" de la tarea activa en docs/ROADMAP.md y contra las reservas vigentes en docs/HANDOFF.md; falla (bloquea merge, no bloquea push a la rama) si el PR toca un archivo reservado por otra tarea activa. Probado con un caso positivo y uno negativo simulado antes de cerrar LF-001.

## Plan de validación y evidencia
Primero escribir criterios de validación de configuración y smoke; implementar mínimo; ejecutar comandos reales, conservar conteos/exit codes, versiones y SHA. Probar instrucciones desde instalación limpia controlada o CI, sin borrar trabajo del usuario. El PR adjunta revisión de dependencias, resultados y riesgos. No incluir costo de llamadas externas ni migraciones productivas.

Riesgos: versiones incompatibles, engines locales distintos de CI, secretos expuestos en cliente, tests vacíos, jobs costosos o falta de navegadores. Resolver setup; defectos o cambios de alcance se documentan. Finalización requiere revisión Claude y aprobación de merge del propietario. Luego LF-002/LF-003/LF-008 pueden reservar archivos y comenzar según ROADMAP.
