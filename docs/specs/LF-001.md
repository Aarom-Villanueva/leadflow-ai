1. Checkout limpio en Node fijado: instalación congelada exitosa sin modificar lockfile; README contiene comandos exactos y limitaciones.
2. Página inicial accesible y endpoint de salud no sensible responden mediante request real. Sin datos demo que aparenten CRM funcional. Config faltante falla con nombre de variable y sin valores.
3. TypeScript estricto, lint y build concluyen sin errores. Vitest ejecuta comportamiento real del validador de configuración (válida/inválida, sin filtrar secretos); no suite vacía.
4. Playwright abre página y comprueba contenido/teclado básico; un fallo de servidor hace fallar la prueba. No acceso a OpenAI ni correo externo.
5. CI reproduce instalación, tipos, pruebas y build; instalar navegadores requeridos con verificación TLS. Actions fijadas por SHA, permisos read-only y sin secretos en PR no confiable.
6. Registrar recursos y límites de hosting candidato, toolchain, compatibilidad de Better Auth/Drizzle y decisión de acceso DB/pooling/RLS pendiente de LF-002. No afirmar aislamiento validado sin integración real posterior.
7. CI incluye un check que compara los archivos modificados del PR contra la columna "Archivos previstos" de la tarea activa en docs/ROADMAP.md y contra las reservas vigentes en docs/HANDOFF.md; falla (bloquea merge, no bloquea push a la rama) si el PR toca un archivo reservado por otra tarea activa. ## Contrato ejecutable de coordinación (LF-001 final)

`npm run test:coordination` ejecuta casos positivos y negativos, incluido CLI contra repositorios temporales. `npm run check:coordination -- --base <SHA40> --head <SHA40> --branch <rama>` valida el diff de tres puntos (incluidos borrados y ambas rutas de renombres). ROADMAP debe contener patrones relativos explícitos en la columna Archivos previstos; HANDOFF contiene registro JSON v1 bajo Registro automático de coordinación. Cada rama corresponde exactamente a una tarea active. Los archivos deben estar previstos y reservados por ella; reservas active de otras tareas, tanto de base como de head, producen exit 1. Una liberación ajena necesita integrarse primero en main: no basta borrarla en el PR.

Durante el primer despliegue de este check se permite base histórica sin registro (main 9c6971b); head siempre exige registro válido. Un registro presente pero inválido falla. El registro, ROADMAP y el script son contratos revisables; CI no es protección ante un colaborador con permiso para reescribir el propio control. La revisión de contratos y protección de ramas siguen siendo necesarias.

El workflow se ejecuta en todos los PR a main: el gate ligero siempre corre, mientras el job de aplicación se omite en cambios solo Markdown/LICENSE. Así no queda un check requerido en estado pending por paths-ignore. Para bloquear integración realmente, un administrador debe exigir Coordination gate en la protección de main; guardar el workflow no configura esa protección. Registrar su estado observado, sin afirmar aplicación si no se pudo verificar por API.

Hosting definitivo sigue diferido por D-001. LF-001 solo verifica Node local, build y servidor local; no declara compatible Better Auth/Drizzle ni valida límites de un proveedor aún no seleccionado. El spike LF-002a precede identidad persistida y negocio.
